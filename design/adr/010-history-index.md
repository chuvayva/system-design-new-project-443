# Составной индекс для истории поездок пассажира

## Контекст и проблема

История поездок (`GET /passengers/{id}/trips`, `passengerTrips` в `src/handlers.ts`) выполняет запрос:

```sql
SELECT id, passenger_id, driver_id, status, price,
       pickup_address, destination_address, created_at
FROM trips
WHERE passenger_id = $1
ORDER BY created_at DESC
LIMIT 20
```

Требование из `design.md`: p95 истории не больше 50 мс на 2 млн поездок.

На таблице `trips` есть только первичный ключ. После `make seed-large` в ней 2 000 031 строка (466 МБ вместе с TOAST и индексами) и 10 000 пассажиров, около 200 поездок на каждого.

План запроса для одного пассажира (`EXPLAIN ANALYZE`, холодный кэш):

- `Parallel Seq Scan on trips`, отброшено 666 610 строк в каждом из трёх процессов;
- затем `Sort` по `created_at DESC` (top-N heapsort);
- прочитано 43 782 страницы с диска и 10 443 из кэша;
- время выполнения 847 мс.

Базовый замер `reports/baseline.md` (числа в `reports/baseline.json`, профиль `load/profile.json`: order 1, read 170, history 5 RPS, 30 с):

| метрика | значение | цель |
| --- | --- | --- |
| history p95 | 85,9 мс | ≤ 50 мс |
| history max | 919,6 мс | — |
| ошибки | 0 из 5334 | ≤ 0,1 % |
| dropped_iterations | 0 | 0 |

Замер берёт только 1000 пассажиров (`__VU % 1000`), поэтому таблица быстро оседает в кэше и p95 под нагрузкой ниже, чем 847 мс на холодную. Но каждый запрос всё равно читает всю таблицу, и время растёт вместе с числом поездок, а не с длиной истории одного пассажира.

## Какие варианты сравнивали

1. **Ничего не менять и полагаться на кэш Postgres.** Отказ: цель уже нарушена (85,9 мс), полный просмотр растёт с таблицей, а при реальных 10 000+ пассажирах таблица в 466 МБ целиком в `shared_buffers` стенда не помещается.
2. **Индекс только по `passenger_id`.** Убирает полный просмотр, но для пассажира с ~200 поездками Postgres прочитает все его строки и отсортирует их ради 20 первых. У частых пассажиров история длиннее, и работа растёт вместе с ней.
3. **Составной индекс `(passenger_id, created_at DESC)`.** Выбран. Индекс отдаёт строки пассажира уже в нужном порядке, `LIMIT 20` останавливает чтение на двадцатой записи, и сортировки нет.
4. **Покрывающий индекс `(passenger_id, created_at DESC) INCLUDE (...)` со всеми колонками ответа.** Дал бы index-only scan, но адреса `VARCHAR(500)` делают индекс по размеру сравнимым с самой таблицей, а у каждой вставки поездки удваивается запись. Ради экономии 20 чтений из кучи на запрос это не окупается.
5. **Читать историю с реплики (`READ_HISTORY_FROM_REPLICA`).** Снимает нагрузку с основной базы, но полный просмотр остаётся полным просмотром и на копии. Кроме того, на стенде реплики нет. Можно добавить позже поверх индекса.
6. **Кэш истории в приложении.** После каждой поездки историю нужно сбрасывать, а холодный запрос остаётся медленным. Это лечит следствие, а не причину.
7. **Секционирование `trips`.** Для 2 млн строк избыточно: одна таблица с индексом укладывается в цель.

## Решение

Добавляем миграцию `db/migrations/007-trips-passenger-history.sql`:

```sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS trips_passenger_created_idx
    ON trips (passenger_id, created_at DESC);
```

`CONCURRENTLY` не блокирует запись в `trips` на время построения. Это важно, потому что заказы идут непрерывно. `IF NOT EXISTS` позволяет перезапускать миграцию повторно, как требует `src/migrate.ts`. Файл содержит одну команду: `CREATE INDEX CONCURRENTLY` нельзя выполнять внутри транзакции, а `client.query` с одной командой транзакцию не открывает.

## Последствия

Хорошее:

- история читает около 20 строк по индексу вместо 2 млн, и время перестаёт зависеть от размера таблицы;
- нет сортировки в плане;
- тот же индекс заменяет отдельный индекс по внешнему ключу `passenger_id` (например, для проверок при удалении пассажира).

Цена:

- место на диске: две колонки по 8 байт плюс служебные данные, 60 МБ на 2 млн строк (`pg_relation_size` после создания);
- каждая вставка поездки (`POST /trips`) обновляет ещё один индекс. При ~9 заказах в секунду в пике это незаметно, но замер заказов нужно сравнить;
- `CREATE INDEX CONCURRENTLY` строится дольше обычного и при сбое оставляет невалидный индекс, который нужно удалить вручную (`DROP INDEX CONCURRENTLY`) и создать заново;
- миграция применяется и к реплике (`src/migrate.ts`), потому что логическая репликация не переносит индексы.

## Подтверждение

1. `EXPLAIN ANALYZE` того же запроса показывает `Index Scan using trips_passenger_created_idx` без узла `Sort` и время выполнения порядка единиц миллисекунд.
2. `make load NAME=after-index` (отчёт `reports/after-index.md`) с тем же `load/profile.json` и теми же данными (2 000 031 поездка):
   - history p95 ≤ 50 мс;
   - ошибки ≤ 0,1 %;
   - `dropped_iterations` = 0;
   - p95 заказов не хуже базового замера больше чем на 10 %.
3. После подтверждения статус меняется на `accepted`, а числа попадают в «Итог» `design.md`.

Откатываем (`DROP INDEX CONCURRENTLY trips_passenger_created_idx`), если план не использует индекс, history p95 не опускается ниже 50 мс или запись заказов заметно замедляется.

Результат: `reports/after-index.md`. History p95 8,0 мс против 85,9 мс в `reports/baseline.md`, ошибок и пропущенных итераций нет, план использует `trips_passenger_created_idx`. Условие про p95 заказов этим прогоном не проверено: k6 не делит время по сценариям order и read (см. «Вывод» в `reports/after-index.md`).
